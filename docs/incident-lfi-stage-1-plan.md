## 本阶段目标

在不改变首页、不影响现有JSA、5Why、会员和法规功能的前提下：

1. 在“专业工具 → 事故学习工具”下提供清晰的LFI闭环介绍入口；
2. 建立多租户、RBAC权限和不可删除审计日志的数据契约；
3. 明确会员权益与业务身份分离；
4. 为后续快速报告、调查、措施和LFI页面保留稳定路径；
5. 第1周不采集事故描述、企业信息、姓名、健康信息或附件。

## 部署边界

本阶段可以部署到GitHub Pages：

- `tools/incident-learning.html`公开介绍页；
- 事故学习工具入口、流程和安全边界；
- 不含业务输入的隐私受限行为事件；
- 数据模型、权限矩阵和测试契约。

本阶段不得部署：

- 真实事故报告表单；
- 客户端本地保存的事故记录；
- 假登录、假审批或仅靠前端隐藏的权限控制；
- 人员伤害、健康信息或证据附件上传；
- 自动事故等级、法定报告或责任结论。

## 架构决定

### 公开网站

继续使用GitHub Pages承载说明页和静态前端。公开仓库不得包含事故数据、访问凭据和受保护附件。

### 会员权益

现有VIP Worker只回答会员是否具备某项产品权益。激活码、昵称或`bound_user`不得充当事故系统中的人员身份或企业租户边界。

### 事故业务服务

后续建立独立的Incident Worker、独立D1数据库和私有R2附件存储：

- 应用会话使用独立的`HttpOnly`、`Secure`、`SameSite=Strict` Cookie；
- 每个业务查询必须由服务端从会话解析`tenant_id`，不接受前端自行声明租户；
- 服务端按`tenant_memberships.role`执行RBAC；
- 业务表包含`tenant_id`，关键关联使用租户复合索引；
- 审计记录追加写入，普通管理员不能更新或物理删除；
- 涉及人员与健康字段和普通事件概要分表存储；
- R2附件只通过短时签名地址访问。

认证首选企业邀请制的邮箱一次性验证码或魔法链接。邮件服务、数据存储位置和账号恢复流程须在第2周实施前由产品负责人确认。

## 核心实体

- `tenants`：企业租户；
- `users`：登录身份，不包含会员激活码；
- `tenant_memberships`：用户在租户内的角色与状态；
- `auth_challenges`：只保存哈希的一次性登录/邀请挑战；
- `user_sessions`：独立应用会话及已验证的活动租户；
- `incidents`：事件概要、分类、实际/潜在后果和状态；
- `incident_persons`：受限的人员与健康信息；
- `regulatory_reports`：人工确认的法定报告提醒与记录；
- `investigations`：调查级别、方法、事实和人工结论；
- `corrective_actions`：措施、责任人、期限、证据和效果验证；
- `lfi_notices`：去标识化的LFI / Safety Alert；
- `rollout_checks`：横向展开范围与验证；
- `audit_logs`：租户内不可删除的关键操作记录。

## RBAC角色

| 角色 | 快速报告 | 查看普通事件 | 调查 | 法定报告字段 | 关闭事件 | 用户与租户配置 |
|---|---:|---:|---:|---:|---:|---:|
| reporter | 是 | 仅本人可见范围 | 否 | 否 | 否 | 否 |
| investigator | 是 | 已授权 | 是 | 否 | 否 | 否 |
| action owner（资源范围） | 否 | 与本人措施相关 | 否 | 否 | 提交措施验证 | 否 |
| ehs_manager | 是 | 是 | 是 | 建议/维护 | 建议关闭 | 否 |
| site_leader | 是 | 是 | 是 | 确认 | 批准关闭 | 否 |
| tenant_admin | 否 | 默认不可见健康信息 | 否 | 否 | 否 | 是 |
| platform_admin | 否 | 默认不可见租户业务数据 | 否 | 否 | 否 | 平台运维 |

前端角色只用于改善界面，任何授权决定必须由Incident Worker重复校验。

数据库契约使用`tenant_id + resource_id`与`tenant_id + user_id`复合外键，阻止一个租户的记录引用另一个租户的事件、LFI或责任人。该约束仍不能替代API层的默认拒绝和跨租户自动测试。

## 六周交付

1. 第1周：公开入口、数据模型、认证/RBAC/审计契约、隐私边界；
